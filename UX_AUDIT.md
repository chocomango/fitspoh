# Fitness Buddy UX and reliability audit

Review date: 8 October 2026. Product: the existing Fitspoh / Fitness Buddy app in this repository.

## Scope and architecture

Reviewed Home, Plans and day editing, guided Train, Overview, History/calendar, exercise browsing/detail/picker, Workout Buddy, gym equipment, Body, Settings, backup import/export, and shared dialogs/navigation. The workflow matrix below separates existing safeguards from new fixes and remaining issues. Code inspection and automated Chromium interactions are evidence; this is not a physical gym study or proof of every combination of actions.

The app is a React/TypeScript static application with hash navigation. `src/main.tsx` owns journal state and serializes automatic IndexedDB writes. `src/store.ts` atomically saves state and a revision, with optimistic conflict checks and cross-tab notifications. `src/workout-actions.mjs` owns set selection, correction, pause, structural changes and bounded persistent Undo. `src/workout-history.mjs` owns finish, reopen, deletion and recovery. `src/domain.mjs` validates version-1 records and derives metrics. `src/mobile.mjs` handles display-unit changes and postponement. `public/sw.js` caches the shell and requested media. There is no backend or cross-device synchronization.

Existing recovery is substantial: the specific accidental-exercise-completion problem already has correction, restarting a set, adding another set, restoring skipped work and durable Undo. Those paths were retained and regression-tested rather than rebuilt.

## UX decisions

- Prefer correction without changing completion status. A copied value is a correction, not evidence that a performed set is unfinished.
- Preserve current entry and return position. Set correction, Undo, pause, reopen and unit changes must restore data as well as screen state.
- Keep editable numbers direct; share persistence bounds instead of adding error dialogs for every keystroke. Overview clamps out-of-range values; guided fields retain the last valid entry. Both prevent writing an unreadable journal.
- Reuse the existing Undo patterns. Active Undo remains a persisted stack of 20 actions; history Undo remains a single in-memory editor snapshot, now covering every editor mutation. It restores the preceding change event, not a grouped typing session. Finish and removal use their separate durable latest-action slots.
- Keep destructive confirmations for plan deletion, body deletion, replacement of logged sets, journal replacement and workout removal. Ordinary corrections, navigation and rest adjustments stay immediate.
- Keep plans independent of actual session adjustments. No automatic target increases, extra dashboards, cloud accounts or unrelated features.

## CI reload follow-up

A later CI run reported 71/72 browser scenarios passing: the straight-set correction test showed the correct 32.5 kg entry before reload but an older 25 kg entry afterward. The test reloaded without awaiting the asynchronous journal commit. Ten ordinary local repeats passed; holding a real IndexedDB read/write transaction ahead of the automatic saves reproduced restoration of an older weight after reload.

`tests/browser/guided.spec.ts` now waits for the journal's **Saved on this device** status before every reload. The affected correction scenario retains a one-second transaction delay to exercise slow storage, without arbitrary sleeps or retries masking the assertions. Ten repeats with delayed storage passed. Application state, persistence behavior and the expected weight remain unchanged. This follow-up does not remove the previously documented risk of forced termination before a pending save commits.

## Remaining risks and coverage limits

Follow-up validation: all 8 guided-workout browser scenarios passed, the delayed-storage correction scenario passed 10 consecutive repeats, lint passed, and `git diff --check` passed. The full 72-scenario suite was not rerun for this test-only follow-up; its earlier complete result is recorded above.

- Existing invalid journals are blocked safely rather than silently rewritten. Recovery from such a journal needs a reviewed valid backup or targeted repair; this patch prevents new oversized entries.
- A hard crash before IndexedDB commits can lose the most recent pending change. Tests cover reload after persistence, failed writes and conflicting tabs; they do not simulate operating-system termination at every transaction boundary.
- Background sound/notifications, OS calls, physical iOS/Android keyboard/gestures, battery policy, browser storage eviction and screen-reader task usability require real-device validation. No claim of reliable closed-browser alerts is made.
- Plan/day and Body deletion have confirmation but no post-confirmation Undo. History Undo does not survive reload and does not group keystrokes. Recovery records are bounded and device-specific.
- Full workout finish still asks for confirmation. Direct save when no unfinished sets remain could remove one tap, but is deferred to avoid changing the established finish pattern without device feedback.
- Headless Chromium tests and code inspection do not prove every combination of timer, history correction, stale plan, unit change and rapid action. Existing tests are retained; significant platform gaps are documented explicitly.
