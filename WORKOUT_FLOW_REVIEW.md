# Workout flow and mistake recovery review

Scope: guided workouts, Overview, saved history, and the persistence paths that protect a live session. Reviewed against the requests for warm-up placement, set reordering, restarting an accidentally completed set, deletion, accidental finish recovery, and repeated Undo.

This is an evidence checklist, not a claim that every possible interaction was tested. The new browser scenarios are in `tests/browser/workout-recovery.spec.ts`. Execution results are recorded below.

## New recovery scenarios

| Situation                                                      | Expected behavior                                                                                                                                                          | Regression evidence                                                                                                                          |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Tap the normal **Add warm-up set** while on working set 2      | Insert before working sets, after any existing initial warm-ups. Preserve completed results and the unfinished working-set draft. Start the new warm-up with its own load. | `default warm-up starts before working sets even when requested from set two`                                                                |
| Request another initial warm-up when warm-ups already exist    | Keep existing initial warm-ups first and insert the new one before the first working set.                                                                                  | `normal warm-up insertion keeps existing leading warm-ups before the new one`                                                                |
| Intentionally insert a warm-up in the middle                   | **Manage sets** offers insertion before or after a specific set. Preserve the IDs and results of all existing sets.                                                        | `explicit middle warm-up insertion preserves each working set and can be undone after reload`                                                |
| Add, reorder, then delete sets                                 | Undo each recorded action in reverse order, including after reload. Do not change the saved routine.                                                                       | `reorder, deletion and extra sets each undo in reverse order across reload`                                                                  |
| Drag a set or use a keyboard instead                           | Reorder sets by identity, preserve the selected entry and results, and provide up/down controls. Touch pointers use the same move action.                                  | `dragging sets and keyboard reordering retain set identities and the selected entry`; `touch pointer dragging moves a set and can be undone` |

Undo restores the skipped unfinished sets and raw input after reload.                                                                        | `skipping an exercise can be undone after reload without losing its draft or completed results`                                              |
| Copy previous session values accidentally                      | Copy the intended completed source, then allow Undo after reload to restore the original numeric values and blank draft fields.                                            | `copying last session values can be undone after reload to restore an unfinished draft`                                                      |

## Limits and deliberate behavior

- Workout Undo retains the latest 20 recorded actions. It survives reload through the journal; it is not a global Undo for saved-plan changes, backup replacement, settings, or every keystroke. Editable input can still be corrected directly.
- The finish-recovery record covers the latest finish, and the removal-recovery record covers the latest discard or history deletion. A later action of the same kind replaces the older recovery record. These are separate from the active session's action stack.
- The history editor's **Undo last history edit** is a separate single-step, in-memory control for the edits that record a snapshot. It does not provide the active session's 20-action history across reload; deleted-workout recovery does persist.
- Undo and restarting a set are different actions. Undo restores the recorded action; **Restart this set** makes the chosen result unfinished so the person can physically perform it again. Later results remain recorded.
- Reopening uses one active session at a time. It must not silently replace another workout. A historical session without a recent finish snapshot can be resumed from its stored results, but discarded raw drafts and old rest countdowns cannot be reconstructed.
- Reversing plan advancement must preserve subsequent intentional plan edits. Reopening is not permission to replace an edited saved routine with an older snapshot.
- Local browser storage remains device-specific. Clearing browser/site data cannot be recovered through workout Undo; an exported backup is the existing recovery path.
- Phone alert delivery with a closed browser or locked phone is outside this change. The current browser alert implementation cannot establish reliable background ringing. Touch reordering passed an automated Chromium CDP touch-input test; physical touchscreen behavior and real-device notification delivery still require device validation.
- Automated flows do not prove every combination of history edits, plan edits, circuit changes, storage failure, and rapid navigation. Any untested combination should be described as untested, not guaranteed.

## Validation run

The coordinated validation passed 71 unit tests, build, and lint. All 48 existing browser scenarios passed in the full regression run; all 18 recovery scenarios passed in the final focused run, for 66 unique passing browser scenarios across the runs. Recovery coverage includes native mouse dragging, keyboard reordering, and automated Chromium CDP touch input.
